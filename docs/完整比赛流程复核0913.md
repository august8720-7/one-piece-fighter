# 完整比赛流程复核0913

日期：2026-09-13。范围：标题、菜单、选人、加载门槛、比赛、设置返回、结算、重赛及教学转人机。此次代码检查和自动测试没有占用浏览器，没有改动中央人物清单、原图或战斗核心。当前新人物素材仍不完整，完整动漫比赛仍由既有资源门槛阻止进入。

## 判断与已修复问题

完整动漫 `scope=full` 的比赛分支已经与动作样板分开：它使用原角色的全部招式，人机／双人有正常开场、有限血气、局胜和整场胜负。样板的输入裁剪、自动补血以及致死后重置，只在 `this.sample` 存在时执行；完整人机／双人不创建该控制器。训练模式自己的无限血气属于用户主动选择的练习规则，不应当在完整训练中删除，但不能带入之后的人机比赛。

本次发现并修复两处实际流程问题：

1. **摄影参数会跟到正式比赛。** 静帧检查使用 `hold=st_c/0`，从训练经菜单或“挑战CPU”进入正式比赛时，浏览器地址仍保留原参数。旧代码在所有模式读取它，导致P1逻辑正常战斗、画面却始终停在指定动作。现在仅训练模式读取 `hold`；人机、双人和重赛忽略该摄影参数，恢复正常动作。训练摄影能力仍保留。
2. **非法样板请求的重试偷偷改变模式。** 对 `scope=sample&mode=cpu` 的直接请求，Fight防御门槛会拒绝，但此前构造失败重试数据时先把mode改为training。现在门槛校验实际请求的模式，失败数据仍保留CPU，重试不会将错误请求变成另一个模式。正常样板依旧要求训练，不降低门槛。

两项修复均在 `src/render/scenes/FightScene.ts`，没有修改伤害、范围、出招时长、物理或资源覆盖要求。

## 已核对的导航与状态边界

| 路径 | 已核对行为 |
|---|---|
| Boot→Title | 普通动漫入口先加载人物资源，再显示标题；不提前创建战斗实例。标题需要能显示的基础资源，但不伪造完整动作覆盖。 |
| Menu→CharacterSelect→Preload | 模式、画风和画质贯通；主菜单的训练／人机／双人／教学均请求完整范围。尚不完整时由Preload明确阻止战斗。 |
| Preload→Fight | 载入、结构及所需动作覆盖先检查；Fight再核对实际纹理。损坏或缺项进入失败页面，不自动回到像素人物。 |
| 样板暂停→Title→Menu | 标题保留样板标识；用户进入正常模式时升级请求到full，仍须经过资源门槛，不存在借菜单绕过的CPU通道。 |
| 完整训练→挑战CPU | 保留角色、难度、画风、画质；去掉教学标记，新建模拟器，有限血气、正常计时和开场。现在也清除摄影覆盖的影响。 |
| Fight→Settings→Fight | 以覆盖层打开设置，战斗与声音暂停；返回使用同一场比赛及表现配置，不重新创建训练对局。 |
| Fight→Result | 正常比赛通过实际KO和局胜推进到整场结束；按确认进入结算，赢家、比分、角色与模式一起传递。 |
| Result→重赛／重新选人／标题 | 重赛回Preload再次检查资源，重新开始的比赛不携带旧HP或比分；另两条路径保留画风、画质和模式所需信息。 |
| 新比赛／重置／退出 | 新建比赛清空前一场投射物ID、动作阶段、胜利语音次数和表现计时；训练重置和场景退出清理对应声音／特效。 |

胜利和KO的表现路径存在，不等于声音素材已具备：当前已正式核实的人物日语语音仍为 **0条**。音效输出、语音素材覆盖和用户实际听感须独立记录，不因为调用了 `phase=win/ko` 就写成“已有人物台词”。
