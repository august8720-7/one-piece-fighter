## 网页回复正文

**建议有条件采用 B，但把“统一重做美术”改成“先证明动作能够稳定生产，再逐批替换表现”。现有精美特效也必须接受返工，不能反过来要求人物、判定和整款游戏迁就它们。**

### 一、诊断：真正缺的是动态制作能力，而非更多精美静图

**附件中可以直接看到：**两张图各包含九种特效设计，并非九帧连续动画。路飞的伸臂、巨拳、火拳都包含实体肢体，不能全部当作附加光效；赤犬素材包含深色岩壳、明亮裂缝和烟尘，需要不同的透明与混合处理。赤犬上中格的火尾触及画布顶边，不宜直接按“完整独立素材”验收。两张图都没有展示身体如何进入攻击、接触目标、收回肢体。

**根据你提供的观察：**低分辨率人物、精细背景与高亮特效确实存在风格冲突，并已出现重复拳体和身体连接问题。我没有看到本地实机截图、舞台原图或运行结果；213 项测试、开发版检查和声音准备情况，均按你提供的状态理解，不视为本轮验证。

**我的判断：**旧方案的问题不只是分辨率不同，更是把“攻击形体”误当成“装饰特效”。但换成高清人物也不会自动解决：身份漂移、脚点抖动、动作断裂、攻击范围失真，都可能在换图后变得更明显。

**支持反方的最强理由：现有连续像素精灵已经承担了动作连续性；B 可能把一个能玩的游戏换成精美但生硬的关键姿势播放器。真正决定路线的变量，是每个合格动作的完整生产成本、正常速度下的连续性，以及与现有判定的匹配程度。**26 个状态、27/26 个招式映射，不能直接换算为原画数量。

### 二、产品与路线：保留格斗游戏，避免全面重做

定位保持：**两角色、一舞台、桌面本地浏览器的 1v1 格斗游戏，优先接近拳皇式攻防手感**，保留本地双人、人机、训练；不转闯关，不增加联机和角色。

| 路线 | 本项目收益 | 主要代价与结论 |
|---|---|---|
| A：统一像素 | 最大程度保住现成连续动作 | 背景、特效仍需重新做像素化设计，简单降采样不足；作为备选，不默认回退 |
| B：统一设计＋关键姿势＋受控补间＋atlas | 符合精美方向，能延续现有运行结构 | 身份与动作生产成本未知；推荐先试产，再扩量 |
| C：全面骨骼或 2.5D | 有利于部分重复运动和后续调整 | 新增拆件、绑定、遮挡和变形制作负担；不作为本轮主线 |
| D：推倒引擎 | 目前没有明确必要收益 | 重做已验证逻辑，却不能解决画风与原画问题；不推荐 |

**保留：**确定性 core、60Hz、整数子像素、种子随机、输入缓冲、比赛流程、事件体系及已有修复。保留逻辑到世界坐标的现有映射，不为高清素材改变攻击距离。

**重做：**角色视觉数据、身体—技能组合方式、采样与尺度规则、HUD 信息层级。移除新美术路径中的整数倍放大、NEAREST 硬编码和巨拳/气球全身缩放；旧美术路径独立保留。Phaser 的过滤方式作用于整张纹理，因此新旧资产应分图集配置，不能指望同一图集逐帧切换采样规则。[Phaser Docs](https://docs.phaser.io/api-documentation/class/textures-texture)

美术目标应是**适合动画的赛璐璐角色**，不是每帧宣传画：轮廓清楚、细节适量、阴影稳定。舞台先做同屏验收，不预先承诺重画；同源裁出的背景和石板带默认同步，不能当成真正独立的远近层强做视差。

### 三、制作分工：模型画姿势，制作流程负责连续性

**设计母版。**沿用已接受的两年后路飞造型。固定头身比、两角身高关系、服装结构、帽子位置、色板、光向和镜头；每次生成引用母版与相邻合格姿势，只改变当前动作。镜头保持横版侧视，身体必要的转体另做关键姿势，不能靠旋转整张图片替代。

**关键姿势与补间。**发力准备、有效攻击、回收、受击、复杂遮挡和橡胶形变由 Image2.5 专门制作。平移、旋转、局部有限拉伸可承担小幅过渡；离线简易骨骼只能作为摆件工具，不能自动解决衣服翻面、关节遮挡或拳头变形。所有结果最终烘焙成逐帧 atlas，不引入运行时骨骼依赖。

**时序。**先读招式的启动、有效、收招、取消与打断窗口，再安排每张姿势持续多少模拟帧。继续由 `stateFrame` 驱动；60Hz 不等于每秒需要 60 张不同原画。禁止均分动作时间，也禁止为了容纳更多画面偷偷延长出招。

**锚点与镜像。**在未裁切的设计画布中定义角色根点、接地基准和肩、腕等连接点；跳跃另保留根点到身体的偏移，不按图片底边找脚。裁切后保存原始尺寸和偏移。Phaser 的 Frame 支持裁切数据与自定义 pivot，图集裁紧不应改变人物站位。[Phaser Docs](https://docs.phaser.io/api-documentation/class/textures-frame) 左右动作先测试镜像，但文字、徽记和非对称特征单独处理；需要独立左向姿势时，两向仍共享逻辑时序。

**不能保证：**同一提示词不会保证身份、服装细节和构图完全稳定，官方也明确提示跨次生成的一致性与精确布局仍存在限制。处理顺序应是参考约束、局部重绘、必要的新姿势，而非不断增加插值。[OpenAI Developers](https://developers.openai.com/api/docs/guides/image-generation)

### 四、阶段计划：先做双机制试产，禁止批量铺招

#### G0：冻结基线，建立动作与来源清单

归档旧可玩构建、当前开发快照、未提交及未跟踪成果。逐招登记时序、位移、判定、现有复用、待补姿势和身体连接需求；先核对开发版真实检查状态。建立来源记录，并给试产设置返工轮次和人工处理预算。

交付是**可回退基线＋动作制作矩阵**，不是宣布“素材规范完成”。

#### G1：首个可操控样板，同时验证两类最高风险

先让新路飞具备站立、进退、跳落、普通拳和伸臂收回；新赤犬先具备站立、格挡、受击，再加入一个大喷火身体变形样板。两角同时出现在现舞台中，带最小 HUD 和首批已核验声音。

必须用真实键盘输入、正常速度检验：空挥、命中、格挡；贴身与最远端；左右朝向、墙角、命中定格和受击打断。慢放只用于定位问题，不能代替正常速度验收。

建议门槛：站姿切换接地误差不超过一个画布像素；无双拳、断臂和全身错误缩放；同招两向有效时序一致；同一输入回放的 core 结果不因换美术改变。同时比较真实操作下“按下—动作启动—接触反馈”的感受。

**没有通过，不生成全招式。**记录生成尝试、透明处理、对齐、补姿势及接入返工的完整成本，不能只统计出图时间。

#### G2：两角同步补齐基础攻防

覆盖现有移动、空中、站蹲防御、受击、倒地起身、投技及状态转换。优先消除空中复用和动作切换断裂，不先把某一角色全部技能做完。

实验分支明确限制尚未制作的动作；旧版保持完整。禁止缺帧时静默回站立，让问题被默认回退掩盖。

#### G3：按机制扩展技能，并进入完整对局

按近身/伸长、投射物、地面范围、空中和变身类分批推进。每批必须连同身体动作、声音、命中/格挡反馈及 HUD 一起通过，再进入下一批。

表现替换阶段冻结招式数值；需要改善平衡时另立变更包，明确修改理由、回归范围和新基线。

### 五、身体与技能必须一起制作

**路飞伸臂：**从发力姿势确定肩点，制作连续的肩—臂—拳结构，以新攻击臂替换身体中的对应部分，不能在完整拳头上再叠一个拳头。伸长路径由招式时序与固有射程决定，不追着对手自动延伸；收招必须表现回弹。巨拳只改变攻击肢体，气球使用专门身体姿势，不缩放整个人。

**赤犬大喷火：**身体前压、攻击臂岩浆化、主拳形成是一套动作，只保留一个主拳。犬头或岩浆拳脱手后转为独立世界坐标实体；附着部件在取消或受击打断时清理，已发射对象按 core 生命周期继续。命中、格挡、相消、落地与出界继续使用现有终止原因区分，不能重新回到“消失就爆炸”。

攻击核需要与有效范围相符；外围烟火可以超出，但不能像另一个有伤害的拳头。不要把整张特效撑满攻击框，也不要反过来按图片改判定。

两张黑底图应分别处理实体、发光和烟：实体保留黑线与岩壳，发光单独叠加，烟保留透明层次。不能把所有黑色直接删除；被裁断或无法可靠分离的素材，退回 Image2.5 修订。

### 六、验收单位是一场愿意重赛的比赛

**声音。**下载合集仍是原料。逐段核对角色、台词、招式和起止时间，再进入 cue 清单；优先游戏日语原声，缺招名用同角色通用出力并标记，不以 TTS 冒充。区分空挥、命中和格挡，检查多段去重、声音抢占及三组音量。首屏真实交互后的声音启动也要验收，因为浏览器可能阻止未经用户交互的音频播放。[MDN Web Docs](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay)

**HUD 与菜单。**生命、气槽、计时和局数具有不同视觉优先级；当前生命立即准确更新，残影条只辅助表达。训练说明可折叠，不常驻遮挡战斗。文字和数值动态绘制，头像等新增美术仍遵守来源要求。教学重点是移动、防守、识别空挥和反击；结算后快速重赛，设置后能顺畅返回。

**CPU。**先判断反复靠近重拳究竟利用了 CPU 决策漏洞，还是招式没有合理反制窗口。前者改防守、距离选择和合法反击；后者进入平衡评审。普通 CPU 应基于可观察状态和有延迟的决策，不读尚未执行的玩家输入，也不靠无限精准防御伪装强度。

**真实复玩。**串行验收“启动—教学—人机—训练—比赛—暂停—结算—重赛”，覆盖两角和本地双人。需要非开发者参与并分开多次体验，记录退出原因、重复策略及是否主动再来一局；无人参与时，明确标注“复玩性未验证”。真实手柄未测就不能宣称支持已验证。

**性能。**在指定桌面环境完成正常比赛与至少十五分钟耐久，覆盖强化八发流星、首次出招、暂停恢复和重复重赛。记录帧时间、加载卡顿、纹理及音频实例增长。PNG 变小不代表显存同比变小；按 RGBA 每像素四字节计算，4096² 单张基础纹理约 64MiB，因此允许每角多页 atlas，不坚持“一人一张大图”。[MDN Web Docs](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices)

### 七、交付、停止条件与来源审计

每阶段交付：可玩候选构建、资产与时序清单、来源台账、正常速度带声音的真实操作录像、判定调试记录、完整检查结果及已知缺陷。脚本录像和真人录像分开标记；最终重新完成 typecheck、lint、test、build，不能沿用旧版通过记录。

所有新增或 AI 重绘的角色、背景、特效、演出图及补帧，生成前核对**官方 ChatGPT 网页 Image2.5 入口与型号证据**。保存提示词、日期、会话、页面截图、原始文件 SHA256；衍生文件记录父文件哈希与处理步骤。“6 Pro”、提示词中的模型名或模型自述都不能替代证据；无法确认，暂停对应生图，不改用 API 或其他模型。哈希证明文件一致性，不单独证明模型来源。

达到试产预算仍无法稳定身份、连接、时序或成本时，先简化阴影与次要细节、缩减演出复杂度；仍失败则停止 B 扩量，提交取舍。**不得靠全身缩放、延长招式、暗删技能或换模型蒙混通过。**旧素材、旧构建始终保留，新版本未通过综合验收不覆盖正式 dist。

### 八、旧方案必须改的五项

1. 从“像素角色不动、叠加精美特效”改为“人物、攻击形体与同屏风格共同验收”。
2. 从“舞台＋流星展示样板”改为“真实输入下的伸臂与岩浆化试产”。
3. 从“按角色批量铺招”改为“先双角基础攻防，再按机制分批扩展”。
4. 从“贴图适配攻击框”改为“身体连接点、动作时序和有效范围共同定义表现”。
5. 从“美术、声音、UI 各自完成”改为“完整比赛、真人复玩及回退能力共同过关”。

真正未定的用户决策只有三项：**试产返工预算上限；预算超限时是否允许首版暂缓少数难招，而非牺牲全部动作质量；真实手柄验证是否作为首版发布硬门槛。**这些不阻碍建立基线与试产计划，也不需要重新确认已经选定的精美方向。
