## 1. 结论与已确认的方向

**项目已经有能完整运行的格斗游戏骨架，但“功能基本齐全”领先于“玩家体验成熟”。接下来应集中打磨路飞和赤犬，让玩家看得懂、学得会、愿意再打一局。**

最强的反方意见是：既然流程、角色、AI、特效都已有，直接增加角色与大招，是否更能带来新鲜感？目前不建议。实查发现 AI 连招策略没有执行，动作图大量复用静态姿势，连基础对局评估都受影响。现在扩大角色数量，会同时放大动作制作、平衡和验证负担。

本次与用户确认的关键取舍：

| 决策 | 已确认选择 | 原因与代价 |
|---|---|---|
| 升级目标 | 可反复玩的朋友试玩版 | 以真实试玩和复玩意愿验收；界面展示效果不能单独代表成功 |
| 美术方向 | **已废止原句「接受统一像素风」**。现规：辨识度不低于设定图基线；先验收单角色正常速度样板。走路缺的是 2D 连续帧，不是 3D 建模，也不再用程序像素人换图集 | 详见 `docs/升级路线0910-修订.md`。原句被执行成 40px 色块人，已回退 |
| 本轮范围 | 沿用双角色、单舞台、本地 1v1，保留人机与训练 | 此为现有项目范围的延续；新增角色、联机等继续留待后续决策 |
| 工作边界 | 本轮做评估与规划 | 没有修改游戏源码、提交、推送或发布；正式升级前按项目约定确认实施方案 |

保留现有 TypeScript + Phaser + 确定性核心，不更换引擎，不为本轮引入后端、账号系统或付费服务。

## 2. 最新进展：哪些是真进步

| 方面 | 当前评价 | 证据与边界 |
|---|---|---|

## 3. 已核实的关键问题

### 3.1 AI 连招策略被提前返回挡住——必须先修

【事实】`src/ai/cpu.ts:82` 在不可操作状态下提前返回；`actionable()`（196 行）不包含 `attack`。而 `decide()` 的连招分支（111 行）要求自己正处于 `attack`。因此通过正常调用路径无法进入该分支。

本次另用临时诊断脚本执行 10 场完整困难 AI 对局，通过角色策略表的 `followups` getter 统计实际读取次数：

| 指标 | 路飞 | 赤犬 |
|---|---:|---:|
| 连招策略表读取次数 | 0 | 0 |
| 攻击状态且 `hasHit` 为真的逻辑帧数 | 10,742 | 12,017 |

后者只是诊断计数，不是有效连招机会数量；零次读取与代码路径相互印证。多段技能自身连中，或者偶发脚本衔接，不等于设计中的命中确认连招策略已经生效。

【推断】该缺陷可能特别压低依赖连招的路飞表现，但尚未用修复前后对照证明它解释了多少胜率差距。

### 3.2 AI 的反应参数没有覆盖所有防御路径

【事实】`cpu.ts:65` 的对手起手检测立即排入防御，随后才设置反应冷却；它不等待难度配置的反应帧数。`cpu.ts:82` 的不可操作分支同样逐帧根据当前招式信息选择防御。

临时诊断中，对手重拳起手后，第一次调用 CPU 输入就返回后方向的样本为：简单 10/20、普通 15/20、困难 20/20。这个统计表示“立即输出防御方向”，不等于实际成功挡住的比例，也不是人体反应时间测量。

应把“只能通过合法按键行动”与“信息和反应像人”分开验收。当前前者有实现基础，后者仍需修复。

### 3.3 自动对局严重偏向赤犬，但暂时不能直接当角色强度结论

【事实】本次运行现有脚本：

```powershell
npx --no-install vite-node scripts/balance-sim.ts 40 normal
```

| 脚本输出 | 路飞 | 赤犬 |
|---|---:|---:|
| 比赛胜场 | 2 | 38 |
| 比赛胜率 | 5% | 95% |
| 回合胜场 | 9 | 76 |
| 获胜回合平均剩余血量 | 29% | 46% |

脚本按比赛交替换边，使用其内置种子序列。数据只代表这套 AI、这组种子与当前参数。先修 AI，再重新评估数值；不要按 95% 这个数直接削伤害。

脚本本身也有不足：达到模拟帧数上限后未先检查比赛是否完成，就依据局分给胜者；局分相同时默认给第二个角色（70 行）。所谓时长统计中还有恒为零的累加（64 行），且当前没有输出平均回合时长。本次没有证明上述超时路径触发，不能因此否定全部结果，但需要先修统计口径。

### 3.4 图集帧名很多，实际姿势很少

【事实】按本地图集 JSON 的不同裁切矩形去重：

| 角色 | 帧名数量 | 不同裁切区域数量 |
|---|---:|---:|
| 路飞 | 150 | 13 |
| 赤犬 | 122 | 10 |

这不是说复用必然错误，而是当前很多“动画帧”只是同一张姿势图的不同名字。`scripts/cut_concept_art.py` 可直接看到：

- 两人的 `walk_fwd` / `walk_back` 都引用 `idle`。
- 路飞 `cr_a` / `cr_b` / `cr_c` / `cr_d` 均复用同一蓄力姿势。
- 橡胶气球映射为站姿，巨人手枪与若干招式复用伸长拳，再由渲染层缩放表现。
- 不足的状态帧重复最后一张姿势；多个帧名指向同一区域。

【判断】优先投入基础移动、防御、受击和普通攻击动画，比继续精修设定图抠边更有价值。每种攻击还要核对“画出来的接触位置”和判定框，不能只验证帧名齐全。

### 3.5 暂停中进入键位设置会丢失当前比赛

【代码确认，未另做实机复现】`FightScene.ts:205` 使用 `scene.start('Settings', { back: 'Preload', ... })`；返回后通过 Preload 重新创建 Fight，102 行会 `new FightSim`。没有保留原比赛状态。

朋友在对局中改键位，预期是回到原来的血量、局数和位置。当前路径会重开，应改成保留战斗场景的暂停与恢复，或其他明确保留状态的方案。

### 3.6 文档状态比实际验收更乐观

【事实】`PLAN.md` 将 M6 标为完成，但原成功标准包含朋友愿意再打一局；本仓库当前未见对应试玩记录。本次也没有真人反馈。

还有具体漂移：规划仍写路飞 1000 / 赤犬 1100 血量，当前两个 `def.ts` 都是 1050；README 写训练默认开启调试面板，当前构造 `DebugOverlay` 传入的是 `false`；规划提到训练慢放和逐帧，本次在已查的训练入口中未找到对应控制。

建议后续分别标注“实现完成”“本机验证通过”“朋友试玩通过”，避免用一个完成标记覆盖三种状态。

## 4. 完整升级清单

优先级定义：**必须**＝影响可靠试玩或当前结论；**优先**＝明显改善复玩体验；**后续**＝本轮不阻塞。以下验收条件是建议目标，不是已达到的结果。序号用于跟踪，不表示可以跳过依赖按行机械执行。

| 序号 | 优先级 | 升级内容 | 具体交付与验收 |
|---:|---|---|---|
| 1 | 必须 | 修 AI 命中确认与取消连招 | 调整攻击状态下的决策入口，尊重核心取消窗口；给两角色各指定一条合法实用连段，固定种子测试证明 AI 真正执行，且无取消权限时不会跳过硬直 |
| 2 | 必须 | 修 AI 观察与反应延迟 | 起手防御、上下段判断、惩罚和拆投分别审查；反应计时不被新分支绕过，既有预判防御可保留；难度差别来自可解释行为 |
| 3 | 必须 | 暂停与设置保留对局 | 改键位、音量后返回，血量、计时、局数、气量、位置保持；重赛才创建新比赛；反复进出暂停无重复按键响应 |
| 4 | 必须 | 修平衡统计脚本 | 正确区分完成、超时、平局；记录换边、种子、参数版本、回合时间、伤害来源；结果可复现，超时不算胜场 |
| 5 | 必须 | 双角色基础连续动作 | 两人均补待机、前后走、蹲起、跳跃、落地、防御、受击、倒地与起身；步伐与位移协调，不再用站姿滑动代替走路 |
| 6 | 必须 | 普通技与特色招式的动作区分 | 轻重、站蹲、空中攻击可辨；橡胶伸缩、气球、二档、熔岩拳和投技表现与机制对应；先完成常用招式样板再扩展全招式表 |
| 7 | 必须 | 统一角色尺寸、脚底锚点与判定 | 左右朝向、角落、跳跃、蹲防都核对；攻击启动—有效—收招逐帧可查；无明显位置跳变、身体忽大忽小或关键接触错位 |
| 8 | 必须 | 可复现的朋友试玩包 | 从干净输入构建，记录素材来源和生成步骤，确认交付包实际包含约定的角色素材；朋友电脑上的画面与验收包一致，避免悄悄退回占位图 |
| 9 | 优先 | AI 修复后再平衡 | 先看接近与反制手段、取消收益、气槽效率、投技风险，再调伤害与血量；分开记录 AI 参数调整和角色数值调整，每次只验证明确假设 |
| 10 | 优先 | 渐进式新手引导 | 按移动与攻击 → 后退防御 → 一招特殊技 → 一条短连段引导；可跳过、可重进；不要求先阅读 README |
| 11 | 优先 | 游戏内出招表与真实键位提示 | 显示中文招式名、方向图示、耗气、用途；随角色朝向和重绑键位更新；菜单明确显示“J 确认 / K 返回”等当前实际按键 |
| 12 | 优先 | 可用的训练面板 | 保留现有木桩与无限血气，增加易操作的重置、受击恢复、连段伤害、指令成功反馈；增加慢放与逐帧供动作校准，不急于做大型编辑器 |
| 13 | 优先 | 双人键盘开局检查 | 提供无小键盘预设、键位冲突提示、两人按键检测；验证同时方向与多键输入，不假设所有键盘都支持足够多键无冲 |
| 14 | 优先 | 手柄、失焦与断连处理 | 手柄可分配玩家；断开有明确提示并暂停；失焦清键与恢复行为一致；至少用实际硬件验证一次双人流程 |
| 15 | 优先 | 特色机制反馈 | 二档持续与疲劳、灼烧、防御、霸体、破霸体用一致图标与效果表达；玩家能解释自己为什么受伤或没打断对手 |
| 16 | 优先 | 打击感与声音成套调校 | 按轻击、重击、格挡、橡胶、熔岩建立反馈层级；核对接触帧、定格、击退、镜头与声音时点；增加音效/BGM 分开控制，提供震屏强度选项 |
| 17 | 优先 | 飞行道具与大招表现 | 犬噛红莲、流星、气球弹反不再主要依赖几何占位；落点与危险区看得清；大招演出短、可辨、不长时间遮挡交战位置 |
| 18 | 优先 | 像素风舞台、UI 与缩放统一 | 舞台增加马林梵多地标与地面层次，降低背景干扰；角色与特效像素尺度一致；根据素材样板调整 antialias、pixelArt 和缩放，避免只替换图集导致模糊 |
| 19 | 优先 | 重赛与换人路径减负 | 保留当前重赛能力，减少多余确认；显示模式、难度、胜者与局分；重赛保留选项，换人可返回，流程不靠刷新网页 |
| 20 | 优先 | 浏览器与性能实测 | 使用同一构建包，在约定的 Chrome/Edge、窗口和手柄条件下测输入、长对局、频繁重赛；记录实际帧时间与对象数量，发现瓶颈再优化 |
| 21 | 优先 | 素材失败回退与加载反馈 | 不只判断 atlas JSON 存在；PNG 损坏/缺失、帧缺失、网络失败均有明确降级与诊断；试玩验收能看出自己正在使用正式素材还是占位素材 |
| 22 | 优先 | 状态、数值与规范同步 | 更新 PLAN、README、角色数值说明；明确当前测试已包含 AI/input/render 纯逻辑；把“角色只加文件”与实际注册方式写准确 |
| 23 | 优先 | 升级基线和回滚记录 | 开工前核对并保存现有未提交工作；按 AI、动作、数值分批记录变更与验收；不将他人现有修改误当本次新增；提交和推送遵守项目权限边界 |
| 24 | 必须 | 真人试玩与问题闭环 | 邀请朋友换边换角色；记录卡在哪里、输赢原因是否能解释、是否主动重赛；修完阻塞问题后复测，不能以自动对局胜率替代真人验收 |

主要代码落点：AI 在 `src/ai/` 与角色 `ai.ts`；流程在 `src/render/scenes/`；输入在 `src/input/`；动作来源与映射在 `assets-src/`、`scripts/`、角色 `animations.ts`；数值在角色 `def.ts` / `moves.ts` 与 `src/core/balance.ts`。只在具体缺陷需要时修改 core。

## 5. 执行顺序与阶段退出条件

### 第一批：修可信度，做一个动作样板

处理清单 1～4、23；同时盘点两角色可用动作素材，先给路飞完成一组“走近 → 轻击 → 重击 → 对手防御/受击”的连续样板。无需先补完所有大招。

交付：可触发的 AI 连招、防御延迟证据、正确统计的自动对局、设置后恢复比赛的实机记录，以及一段正常速度的基础动作演示。

退出条件：上述代码缺陷关闭。美术样板必须仍能认出角色；脚底稳定、接触可读。样板没通过，不批量切全角色素材。不能按“帧名已齐”或“统一像素风”估算工作量。无走循环源时第 5 条保持阻塞。

### 第二批：让两个角色真正动起来

以清单 5～7、15～18 为主。先补两人的基本功，再补使用频率高的普通技与核心特殊技，最后处理终极技和演出。保持一个可运行构建逐批替换。

交付：两角色连续动画、匹配的判定、清晰的格挡/霸体/二档反馈、统一舞台与基本音画节奏。

退出条件：从正常速度的对战画面能分辨进攻、防御、受击和倒地；基础动作无明显滑步、抖动和接触错位。这个阶段的成功不是“更高分辨率”，而是“动作表达准确”。

### 第三批：让朋友不需要口头教学也能开始

处理清单 9～14、19，第一次小范围试玩应在这一批内发生，而不是所有包装完成后再做。

交付：新手引导、实时键位出招表、可使用的训练界面、双人输入设置、难度调整与第一轮反馈。

退出条件：朋友可以独立选人、进入对局、找到防御与一个特殊技、完成比赛并重赛。若仍频繁卡在操作，优先修引导和输入；不马上增加简化操作系统等新的规则分支。

### 第四批：稳定交付，按复玩反馈收尾

处理清单 8、20～22、24，并关闭前三批遗留阻塞项。

## 6. 朋友试玩版验收建议

以下数量是本轮建议验收门槛，并非已经取得的数据，也不是统计学上的市场需求证明。

| 维度 | 建议门槛 |
|---|---|
| 代码 | typecheck、lint、现有测试和 build 全过；为本次修复补能复现缺陷的测试，避免只增加镜像实现的测试 |
| AI | 两角色指定连段可复现；新增观察后不能绕过设定反应延迟；修复前后使用同种子、同角色数值做对照 |
| 平衡 | 换边、多种子、分难度记录；沿用 35%～65% 只作自动对局报警区间，不作为真人平衡合格证；异常必须能追到招式或策略原因 |
| 基础可靠性 | 同一验收包连续完成 20 次开局—结算—重赛，无崩溃、卡死、输入失效；设置返回保持原对局；损坏素材可诊断 |
| 输入 | 覆盖一套双人键盘和一套真实手柄配置；无小键盘也能完成双人开局；失焦/断连不导致无提示丢局 |
| 画面 | 两角色基本状态及主要攻击清晰区分；逐帧检查之后还必须正常速度检查；在选定桌面尺寸下能读清血量、气槽与提示 |
| 性能 | 在记录了设备、浏览器和分辨率的条件下，正常对局以 60 FPS 为目标；记录波动与连续游玩结果，不把固定 60 Hz 逻辑当作画面稳定 60 FPS 的证明 |
| 新手体验 | 至少 3 位朋友试玩，包含不熟悉格斗操作的人；目标在 5 分钟内不靠旁人指导完成开局、基本攻击/防御和一次特殊技 |
| 复玩 | 每位朋友有换边换角色的机会，记录是否主动再来一局及理由；至少 2 位愿意继续玩，且不存在仍未解决的共同阻塞问题 |

若朋友不愿重赛，先识别原因是看不懂、按不出、打不过、缺乏选择，还是单纯不喜欢题材；只修能够解释流失的问题，不把所有反馈都转换成新功能。

## 7. 本轮明确后置

| 后置项 | 现在不做的理由 | 重新考虑的条件 |
|---|---|---|
| 第三个及更多角色 | 现有两角色动作与对局尚未成熟，增加角色会扩大战斗组合与制作成本 | 两角色通过真实复玩验收，且已有可复用的动作生产方式 |
| 联机 rollback | 确定性只是前提，还需快照恢复、输入传输、预测纠正、掉线与兼容处理 | 朋友确实需要异地对战，且现有体验已证明值得联机 |
| 3v3、剧情、街机模式 | 会扩展规则与内容，不能修复当前基本动作和人机缺陷 | 1v1 复玩主要受内容量限制，而不是操作与手感 |
| 触屏、Electron/Tauri | 新增输入或运行环境，当前目标是桌面浏览器 | 目标用户真实提出平台需求 |
| 完整回放产品、在线排行、账号 | 与首轮朋友试玩关联弱 | 有明确复盘/比较需求；此前可先保存用于诊断的输入与种子 |
| 大型判定框编辑器、全面拆分重构 | 容易变成开发工具项目 | 小工具已无法支撑实际动作数量，或具体修改被现有结构持续阻塞 |

朋友试玩继续遵守项目现有的素材与分发边界；能本地生成图集，不代表具有公开发布许可。本轮不包含公开部署决策。
