# 声音加载结构核对1009

接续1008单条实际RAM余量失败，仅只读核对已安装Qwen/Accelerate源码、原权重头和1008票据；没有第二次native运行。安装源码SHA与当前资源在D盘 `resource-budget1008/audit/loader-memory1009/installed-loader-evidence1009.json`。

## 输出声音模块已关闭

【事实】现有QA入口已经在 `from_pretrained` 传入 `enable_audio_output=False`，并立即要求 `model.has_talker` 为False。生成也使用 `return_audio=False`。已安装Transformers 4.57.6的Qwen实现第3706–3714行只在 `config.enable_audio_output` 为True时创建talker/token2wav；`disable_talker` 删除同一对模块。通用配置加载会把kwargs中的已知配置字段覆盖到内存config，原磁盘config中的True不代表本次仍开启。

【事实】原BF16权重头：thinker 9,406,928,896、talker 769,209,856、token2wav 1,796,205,184字节。此次实际GPU参数5,701,515,264加CPU backing 3,705,413,632，恰好等于全部thinker。两个输出声音模块共2,565,415,040字节没有进入本次模型模块；不能把重复关闭它们当作新的省内存修复。官方包装仍读取259,544字节的 `spk_dict.pt`，这是现有speaker字典，不能把它夸大为GB级TTS权重。

thinker自身固定构造完整audio_tower、visual、文字decoder和lm_head。audio_tower 1,275,353,088字节完整保留；visual 1,337,368,576字节在此次GPU上，但请求没有image/video输入。现有官方构造没有与 `enable_audio_output` 同义的“关visual”参数，不删除它或改模型结构；CPU显式visual-disk属于旧独立路径，其15GB规则仍保留。

## CPU backing不等于CPU执行

【事实】当前Accelerate `big_modeling.py:382–405` 将标为CPU的模块放入内存weights_map，实际execution_device仍为主GPU；`hooks.py:364–394` 在forward前搬上GPU，`post_forward` 恢复meta占位。1008的CPU map覆盖decoder第16–35层、norm/rotary/lm_head，共242个真实BF16 CPU tensor。内存权重表不含disk index/folder，实际deviceMap也不含disk。它有RAM与PCIe搬运成本；“GPU6”是常驻预算，不能理解为整次活动只有6GiB。

此次峰GPU allocated 6,407,511,552字节是torch实际分配统计；没有记录CUDA reserved/driver host allocator，不能据此倒推出完整主机内存。

## Private、工作集和全机RAM各自证明什么

| 时点 | 本进程Private字节 | 本进程工作集字节 | 全机可用RAM字节 |
|---|---:|---:|---:|
| 加载前仪表第一采样 | 1,819,385,856 | 651,227,136 | 14,245,007,360 |
| 模型加载完成 | 14,065,065,984 | 1,556,807,680 | 13,425,221,632 |
| 音频生成31.750秒 | 16,333,516,800 | 6,736,224,256 | 8,128,995,328 |
| 音频生成81.781秒、已请求停止 | 15,728,685,056 | 9,279,995,904 | 2,112,499,712 |
| 音频生成111.343秒、等待forward结束 | 16,332,144,640 | 9,862,971,392 | 589,840,384 |

Private是进程提交的私有内存，可能含尚未驻留的页；工作集是当时驻留在物理RAM的页；全机可用RAM还受其他进程、驱动和Windows缓存影响。这三列不能相加，也不能用CPU权重3.705GB充当整进程RAM上限。

【推断】加载后的非驻留/驱动/搬运与随后触及的页解释了“权重表不大但生成时工作集持续长大”的一部分。原采样没有其他进程同期工作集、CUDA reserved或主机分配器明细，因此**不能定量断言全部RAM崩降来自哪个模块，也不能断言Ollama是这次唯一原因**。修正前置条件按实际观测Private峰16,333,516,800加2GiB安全余量：18,481,000,448字节，守护检查只请求下一次停止检查退出，不能中断当前forward。

磁盘方面，1008最终证据目录72,694字节，cache增量0，老候选/模型/来源表没有写入。解决旧15GB门槛只解决了错误的磁盘前提，未解决这次RAM稳定性。

## 当前断点与最小后续方法

2026-10-09T01:52:50 UTC只读观测：RAM余7,399,911,424、GPU余3,443,523,584字节，均不足新的GPU6条件。1008完整SHA证书已超过新入口6小时有效期；条件恢复后再做一轮fresh SHA和明确资源交接，先1句稳定实证；不能用旧证书、旧加载完成或部分原文扩到其余105句。

没有发现漏关talker可用来修复，所以本轮不再改这个选项。未来若评估全CPU无disk，应先在原隔离环境做一次单独小矩阵BF16/SDPA能力进程，记录实际退出码，再在完整权重与活动余量同时满足时才做一条；旧 `torch_cpu.dll/0xc0000005` 保留，不能机械重复整个加载，也不能把纯矩阵探测当声音通过。本轮仅提出这一验证方法，没有执行CPU探测或加载。

旧119候选、14稳定响应和2歧义保持；1008新增0稳定通过、0采用。根代理可恢复游戏资源，本子任务无重模型存活。
